嗨，欢迎收听本期的技术精读。今天咱们来聊一篇特别有意思的文章：如果你同时盯着代码评审、群聊反馈和 CI 报错，脑子里估计已经开始打架了。

这篇文章叫《Super-agent 设计探索》，来自 DeepSeek Harness 团队。它讲的不是某个已经上线的产品功能，而是一套面向未来的 Agent 架构：让人的角色从亲手执行，逐步上移到决策和验收。

现在很多 Coding Agent 都以 Session 为基本单位。你在会话 A 里修 Bug，会话 B 里做功能，会话 C 里看测试，彼此的上下文完全隔离。人一次能盯住三五个活跃任务，就已经快到注意力上限了。

文章提出，瓶颈不该继续压在模型能力上，而应该压在人的记忆和切换成本上。所以他们把 Agent 设想成一个跨会话存在、长期在线的连续实体，也就是 Super-agent。

它有四个关键词：连续、高效、主动、持久。你在 IM 提方案 A，到 GitHub 评论里改成方案 B，它还记得前因后果；多个任务可以并行推进，也能主动观察环境，必要时再出手。

难点在于，单个 ReAct Loop 很难同时满足这些条件。于是整套架构拆成五块：双层会话、事件驱动、面向人的交互、计算状态与环境分离，以及负责兜底的 Watchdog。

先看最关键的双层架构。你可以把它想成一个前台总协调员，加上一组互不打扰的后台执行工程师。Router 统一接客和分派，Worker 各自闷头干活，用户看到的却始终是同一个 Agent。

Router 是常驻大脑，负责跨任务记忆、对外沟通和整体协调，但原则上不亲自跑 Bash、也不亲自执行具体任务。它更像会议室里的项目负责人，只决定哪件事交给谁，而不是亲自钻进去写代码。

这里有个反直觉现象：事件一多，Router 反而可能更省。上一轮推理期间到达的事件会先积压，下一轮再合并处理；哪怕触发速度从每分钟一条涨到四十条，每个决定分摊的推理时间反而降到原来的四分之一。

原因也不玄学。Router 通常是长输入、短输出，多条事件合并后可以共享一次预填充成本。就像窗口前排了二十位同事，前台一次叫进四个一起问，总耗时不等于二十次单独叫号。

真正干重活的是 Worker。每个 Worker 都有独立上下文和完整工具，通常还需要更强的模型。它可以继续拆子任务，也可以组自己的 Agent Team，但这些内部复杂度不会泄漏给用户。

Worker 不直接插话。所有进展先汇报给 Router，再由 Router 统一回复。这样多个任务同时成功或失败时，你不会收到五套互相抢话的消息，只会看到一个有条理的结论。

接下来是主动性的来源。Agent 的输入不再只有你敲下的提示词，还包括群聊、邮件、日程、代码评审评论和 CI 结果。这些环境事件被称为 Trigger，相当于随时可能响起的门铃。

但真实工作流里的门铃，九成以上都是噪声。文章借鉴 Fast Path 和 Slow Path：先用确定性代码按来源、群组和白名单快速过滤，只有候选事件才交给模型判断要不要行动。

过滤之后，路由也不能每一步都经过 Router。系统会把同一个 PR、同一个聊天话题或同一封邮件串视为一条 Thread；Worker 一旦订阅它，后续消息就直接送到那里，不必再让总协调员中转。

这种订阅还是多对多的。一个 Worker 可以关注多个 Thread，同一个 Thread 也能同时通知多个 Worker。它们因此能看见彼此的动作，并有机会自行化解冲突，而关键结论仍统一汇总给 Router。

接下来是模型上下文怎么装。上下文窗口有限，塞太多会稀释注意力，塞太少又会让模型反复调用工具。文章把它当成缓存：近期大概率用到的信息直接 Inline，长内容则 Spill 到窗口外，只留摘要和续读入口。

更进一步，Trigger、Thread 和 Worker 都拥有唯一 ID，注入时顺便带上关联对象的 ID。模型需要更多背景时，就能像顺着链接逐层点开一样召回，不必一次塞进全部历史，这就是链式召回。

文章还借鉴了 CPU 的投机执行。收到会议邀约时，助手可以先在后台查日程、找资料、起草回复；群里有人报错时，Agent 可以先复现问题、尝试修复，成功才交付，失败就安静丢掉。

这意味着 Agent 不必把所有事都拖到用户确认后才做。多花一点后台算力，换来更短的人工等待，也让它能在讨论还没结束时就悄悄准备交付物。

交互层面，经典 ReAct Loop 像对讲机：工具一运行，整个会话都卡住。异步版本则把耗时命令改成启动和停止，启动后立刻返回“已在运行”，后台完成时再把结果作为新事件送回来。

所以你不必等一个测试跑完，才回复下一条消息。前台聊天和后台执行可以同时进行，这种更像人类同事边干活边接话的全双工体验，才算真正的高效。

输出还必须适应不同信道。IM 里应该低打扰、少废话，最好别把几十步推理全倒给群友；而 GitHub、邮件和文档里，则需要完整的问题背景、改动说明与验证结果。

更关键的是，Super-agent 不能被某台电脑绑住。文章先把 Agent Loop 放到云端，把会话状态存进数据库；再把本地代码、私有凭据和工具链留在原处，只装一个轻量守护进程按需执行命令。

这就像大脑和双手分开。你可以接入自己的开发机，也能接入云端机器；个人电脑离线时，云端 Agent 继续工作，等设备重新上线，再补跑必须依赖本地环境的任务。

长期在线还离不开外部兜底。Watchdog 相当于系统之外的 Control Loop，不只检查进程死没死，还会判断 Worker 是不是陷入无效循环、方向有没有偏离，异常时直接介入修复。

文章也做了初步实验。完整方案的任务中位完成时间大约十二分钟，明显比依赖提示词调用 Subagent 的单会话方案更稳定；代价是多会话会消耗更多缓存 token，而且实验仍基于合成负载。

更有意思的是，去掉事件直通后，任务几乎没变慢，Router 却多做了约三成决定，缓存 token 多出近四成。也就是说，直通主要是在省中央调度成本，而不是让任务本身变聪明。

当然，这套设计还有不少开放问题。规模扩大后，Router 怎么切分，多个 Agent 如何跨边界协作，跨月级别的长期记忆怎么保存，以及脱离 Session 后用户究竟该怎样管理任务，都还没有标准答案。

安全更是硬门槛。云端 Agent 一旦被提示词注入攻破，可能波及所有连接的设备；而凭据只要进入模型上下文，就可能泄露。如何让 Agent 使用凭据却永远看不到凭据本身，是必须补上的课。

整篇文章最值得借鉴的，其实不是某个具体框架，而是把经典计算机系统思想搬进 Agent 世界：分层调度、事件驱动、缓存局部性、异步执行、存算分离、外部看门狗。

最终目标是让 Session 退回实现细节，让用户不必操心上下文拼装。Super-agent 也就不只是等你下命令的聊天窗口，而是一个能在真实工作环境里持续在线、主动推进事情的数字协作者。
