过去一年，Coding Agent 已经证明，模型可以借助工具独立完成相当复杂的任务。真正限制生产力继续提升的，正从模型能不能干活，转向人的注意力能不能同时盯住更多任务。

现有 Agent 大多仍以单个 Session 为基本单位。你在 IM 里提一个需求，切到 GitHub 又要重新交代背景，同时推进三到五条工作线，还得自己记住每条任务停在哪里。作者把突破这一限制的 Agent 形态称为 Super-agent。它追求四个特征：跨渠道保持连续、并行处理多项任务、主动观察环境，以及长期在线并自动恢复。

最关键的架构洞察，是把“全局连续性”和“高并发执行”拆开，也就是 Router 与 Worker 的双层架构。

Router 是常驻的全局协调层，承接所有入口，维护跨任务记忆，判断新任务该交给谁。Worker 则拥有彼此隔离的上下文和完整工具，专注执行具体工作。两者如果合并在一个 ReAct Loop 里，任务一多，响应就会被串行推理拖慢，上下文也容易混杂。但如果每条消息都新建独立 Session，并发虽然高，任务之间又会失去联系。

双层架构的价值，就是让 Session 退回实现细节。用户不必记住“Session X 里说过什么”，面对的始终是同一个 Agent。需要注意的是，Router 不需要最强模型。它通常只做高层路由，任务量大时还能把积压事件批量交给模型。实验显示，事件速率从每分钟一条升到四十条时，平均批量从一条增加到二点八条，单次请求只从二点五秒涨到三点九秒，每个决策分摊的推理时间反而从六点四秒降到一点六秒。

第二个关键洞察，是 Agent 的驱动方式要从人工提示词变成环境事件。群聊消息、邮件、代码评审意见和 CI 结果，都可以成为 Trigger，让 Super-agent 不必一直等用户下令。

但真实环境里的事件噪音极高，绝大多数群聊消息都不值得处理。系统因此采用类似计算机系统 Fast Path 与 Slow Path 的两级过滤。先用确定性代码检查来源、群组和白名单，把明显无关的事件挡在模型之外；只有通过准入的候选事件，才交给 LLM 判断是否值得行动。这既降低成本，也把自然语言策略保留为可随时调整的扩展点。

事件有了明确归属后，也不必每次都绕经 Router。同一个 Pull Request、同一个 IM 话题或同一封邮件往来，构成一条 Thread。Router 为新任务创建 Worker 后，Worker 直接订阅对应 Thread，后续事件由程序直通。Thread 与 Worker 是多对多关系，多个 Worker 遇到同一个共享环境时，也能同时收到通知，自行发现冲突。

第三个洞察，是上下文应该像 Cache 一样管理。信息太少，模型就要反复调用工具；信息太多，又会挤占窗口并稀释注意力。Inline 与 Spill 的组合，是把近期很可能使用的信息直接放进上下文，把低频或超长内容留在窗口之外，只保留摘要和引用。再给事件、Thread 和 Worker 建立唯一 ID 与引用关系，就能形成链式召回：模型从当前事件出发，沿关联逐跳找回旧任务，而不必把全部历史常驻在 Router 窗口中。

系统还借鉴了投机执行。收到会议邀约时，Agent 可以先检查日程、搜集背景并准备草稿；群里有人反馈缺陷时，它可以在后台静默复现并寻找修复。只有结果真正有价值，才提交 Pull Request 或通知用户，否则就丢弃。这样做会多消耗一些后台算力，但能显著减少人的等待与介入。

要让这些能力真正可用，还需要解决交互与持久运行问题。耗时的工具调用被改造成异步启动与停止，后台执行期间，前台仍可接收新指令，这就是从半双工走向全双工。不同信道也要采用不同的输出方式：IM 里坚持低打扰，只在需要决策或验收时发短消息；GitHub 和邮件则提供完整背景、改动说明与验证结果。

持久在线则依赖计算、状态和执行环境分离。Agent Loop 放在云端弹性计算中，会话状态存入数据库，本地开发机只运行一个轻量 daemon，负责执行命令和返回结果。这样既不必复制包含私有凭据、内网依赖和未提交修改的完整环境，也能让 Agent 在设备重新上线后继续工作。系统外部还需要独立的 Watchdog Session。它不仅检查进程是否存活，还判断 Worker 是否陷入无效循环、是否偏离目标，并通过自然语言修改提示词或触发规则。

初步实验也支持这套路线。测试包含约三百条消息，其中只有二十条工作请求，每种方案重复五次。Super-agent 的完成时间中位数是十二点四分钟，百分之九十五分位是十五点七分钟，明显优于依赖提示词决定是否委派 Subagent 的单 Session 方案。去掉事件直通后，完成质量基本不变，但 Router 决策增加约三成，读缓存 token 增加约百分之三十七。也就是说，额外会话成本换来了更快、更稳定的结果，而直通机制有效降低了全局协调开销。

不过，这仍然是一套面向工程实践的架构探索，而不是正式产品能力。Router 何时需要分片、长期记忆如何扩展、人如何接管长期运行的任务、不同 Agent 之间如何安全协作，都还没有定论。尤其是云端 Loop 连接本地设备，会引入提示词注入、凭据泄露和横向控制等安全风险，这些必须随着架构一起解决。

Super-agent 真正带来的启发，是 Agent 产品的竞争焦点正在从一次对话的聪明程度，转向长期运行系统的工程能力：会话如何解耦，事件如何路由，上下文如何按需召回，任务如何异步执行，异常如何恢复。最值得关注的不是某一个提示词技巧，而是这些模块背后的系统边界与 Trade-off。对照原文中的整体架构图、端到端曲线和批处理实验，再深入阅读 dsh-superagent-prototype 源码，你会更容易看出，这不是给传统聊天 Agent 加一层长记忆，而是重新定义 Agent 如何持续存在于真实工作环境里。
