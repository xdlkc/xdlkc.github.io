嗨，欢迎收听本期的技术精读。今天咱们来聊 Harrison Chase 写的一篇很有意思的文章，题目叫《如何构建知识工厂》。先想象一个让人抓狂的场景：Agent 写代码飞快，可一让它按公司规矩出报表，就开始找错数据、乱改口径，活像个聪明但刚入职的新人。

有人会本能地换更强的模型，再多塞些上下文。但文章说，真正决定 Agent 能不能像熟练员工一样干活的，往往是知识：公司怎么定义指标，数据放在哪，以及哪些经验必须遵守。

这些知识平时藏在哪儿？藏在一线员工的脑子里，也散落在 Notion、Slack、Wiki 和一次次对话中。很多事根本没写下来，新人只能跟着老同事跑几遍，才慢慢知道该找谁、该信哪个数据源。

上下文，是 Agent 此刻手头拿到的信息；知识，是持续维护、以后还能复用的理解。就像桌上摊着今天要用的材料，而老师傅知道这些材料该怎么拼、哪一步不能省。前者会过期，后者让工作越做越稳。

所以，知识工厂就像软件工厂的升级版。软件工厂让顶尖工程师搭系统，把编码交给 Agent；知识工厂则把散乱经验加工成可复用的流程和规范，再把通用知识工作交给 Agent。

那要维护哪些知识？翻来覆去无非三类。技能，也就是“公司希望事情怎么做”的流程、指令和脚本；过去靠同事口口相传的东西，现在得尽量写下来，变成 Agent 能执行的步骤。

另一类是领域知识，讲的是产品、客户、竞争对手和组织规则。它的变化通常没那么快，可文档往往又大又旧，缺一块、错一句，都可能让 Agent 自信地答错。

还有一类是数据访问指南：哪个库是可信来源，数据存在哪，怎么查询。如果 Snowflake 或 Databricks 已经完整又及时，就别急着复制一份影子数据；把入口、字段和查询方法讲清楚更重要。

真正有用的工厂，得有三根柱子：让 Agent 报告知识缺口的后台机制、负责修修补补的整理 Agent，以及存放知识的仓库。少任何一根，闭环都转不起来。

先说缺口报警器。Agent 被要求做某件事，却找不到答案，或者发现资料已经过时，就应该立刻标出来。最好还能附上证据，甚至给出建议，让问题不是消失在对话里。

那谁来修？文章建议交给专门的整理 Agent，在后台定期跑。因为正在干活的 Agent 往往只顾完成眼前任务，知识库乱一点、互相矛盾一点，它也未必愿意管。

整理 Agent 要能看到所有原始材料，比如 Notion、Slack、Wiki，还要读取运行轨迹，找出大家到底在怎么使用 Agent。它把报错、人工纠正和反复出现的操作，沉淀成新的技能与规范。

仓库本身反而没那么神秘。技能可以放 GitHub，简单知识可以放 Notion，也可以用 OKF 存进 LangSmith Context Hub，或者用 Neo4j 建知识图谱。整理 Agent 得知道怎么和这些格式打交道。

这里也别急着站队。行业开始用 Skill 表示程序性记忆，也就是“该怎么做”；但语义性记忆，也就是“事实是什么”，还没有统一标准。格式可以试验，系统却别做得太僵、太复杂。

来看一个端到端例子。Agent 要做营收报告，原始数据放在 BigQuery 和 Salesforce；同时还要知道怎样按 LangChain 的风格写报告，怎样计算 ARR，以及怎样访问那些快速变化的数据。

于是知识被拆开存放：报告技能在 GitHub，长期业务口径在公司 Wiki，BigQuery 和 Salesforce 的访问方式则作为技能放进 Context Hub。原始数据负责提供事实，知识负责告诉 Agent 该怎么使用事实。

运行中，Agent 发现 BigQuery 的一列被重命名了。它没有硬猜，而是找到正确列名，并通过问题上报工具标记缺口，同时建议更新。知识缺口不是靠人偶然发现，而是从工作现场自动冒出来。

报告生成后，财务负责人又和它实时协作，修了格式，还告诉它所有 LangChain 文档都要换新页眉。你看，这句临场纠正如果没被接住，明天还会重复犯错。

到了晚上，整理 Agent 处理白天留下的标记，再检查这次运行轨迹，从财务负责人的来回沟通里提炼新规则。它更新技能：取数使用新列名，起草报告使用新页眉。

这才是知识工厂的核心：不是开工前把一切都写完，而是让 Agent 在真实工作中暴露无知，再把修正沉淀下来，让下一次做得更好。你不必一开始覆盖整家公司，先挑一个高频流程跑通闭环就行。

LangChain 已经在内部的 GTM、内容工作室 Agent 和 LangSmith Engine 中实践这套体系，也正带着客户把它引入更多 Agent。想在自己的团队里搭一座这样的知识工厂，作者团队也明确表示可以提供帮助。
