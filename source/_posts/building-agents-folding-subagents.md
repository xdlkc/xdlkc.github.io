*Building agents: When to fold subagents into your main agent loop*

在 Claude Platform 中构建智能体时，减少子智能体（Subagents）的数量、转而采用渐进式披露（Progressive Disclosure）的上下文与工具，不仅能提升输出质量，还能降低成本与延迟。本文将介绍何时以及如何进行迁移。

<!-- more -->

> 迁移提示（Migration Kit）：如果你已在 Claude Platform 中构建了包含多个子智能体的智能体系统，可以使用我们的迁移工具包（Migration Kit）来评估哪些子智能体适合并入主智能体循环。该工具包会运行一套引导式工作流，用于识别现有架构模式、评估替代方案并验证最佳路径，同时还附带一个可在接入真实智能体前先行试用的模拟系统演示（Demo）。

子智能体（Subagents）——即拥有独立上下文窗口、专属工具集和指令，并由协调器（Coordinator）统一编排的智能体——是智能体架构设计的核心组件。它们在结果验证、并行任务处理以及模块化权限控制方面表现出色。我们在使用 Claude Platform 构建的诸多内部智能体中也广泛采用了子智能体，例如我们的多智能体研究系统（Multi-agent Research System）。

然而，近期我们的应用 AI（Applied AI）团队在多个企业级智能体部署案例中发现了一种普遍趋势：将路由器（Routers）、规划器（Planners）以及各领域子智能体（Domain Subagents）并入主智能体循环（Main Agent Loop）往往能带来显著收益。在对多个企业部署进行的对比评测中，搭载技能（Skills）的单智能体架构在输出质量上频繁优于“ 单提示词包揽一切（One-prompt-for-everything ）” 设计和“ 多子智能体（Subagent）”设计，且单次任务的成本与延迟通常更低。

例如，某家企业发现其面向客户的智能体内部包含了十几个专家子智能体，这不仅导致难以维持一致的品牌体验与沟通语调，还引入了明显损害用户体验的响应延迟。

此外，我们也经常看到许多拟议的智能体设计方案遵循着一套似曾相识的演进路径：底层是意图分类器、固定的多步推理流水线、用户分群桶（User-segment buckets）以及各自独立的推荐分支，顶层再架设一个多智能体编排器（Multi-agent Orchestrator）。

在这些案例中，实践反馈往往表明：上述绝大部分架构结构都在替模型做它如今早已不再需要外部代劳的工作；实际上，仅需一份清晰的系统提示词（System Prompt）、4 至 5 个轻量级数据工具（Thin Data Tools）以及明确的输出护栏（Output Guardrails），就足以覆盖绝大多数业务场景。

*图 1：传统多层路由与专家子智能体流水线（左）与基于渐进式披露的单智能体主循环架构（右）对比（对应原文图：subagent design）*

需要明确的是，子智能体依然有其不可替代的用武之地（包括在前沿研究领域）。在以下场景中，仍应使用子智能体：

- 单智能体循环因上下文膨胀（Context Bloat）而出现可量化的性能退化；或

- 需要使用独立的全新上下文窗口并行处理多项任务，且这些窗口在任务完成后即可直接丢弃；或

- 单个智能体难以从大量工具中准确选择合适工具，或系统提示词中存在相互冲突的指令。

但我们在实践中过于频繁地看到，许多企业为每个团队或每类问题都单独分配一个子智能体，最终导致智能体架构完全演变成企业组织架构图的翻版（即“康威定律 Conway's Law”在智能体设计中的体现）。

本文将结合我们在大型组织中构建智能体所积累的最佳实践，详细阐述何时应考虑将子智能体并入主智能体循环。

## 大型组织构建智能体的常见失效模式 (Agent building failure modes for large organizations)

企业通常希望构建一个能够将多项产品与业务能力整合到单一客户交互界面中的统一智能体。

通常情况下，每项业务能力归属于不同的团队，因此企业最初往往让各个团队分别构建自己的专属智能体，随后再由中央平台团队在顶层构建一个编排器（Orchestrator）。这种做法可以衍生出多种架构形态，包括“编排器-子智能体（Orchestrator-Subagent）”架构，或将特定智能体封装为 MCP 工具暴露给单个主智能体。

这看似是最简单直接的解决方案，但会立刻在以下几个维度引入严重的复杂性：

- 上下文管理（Context management）：你必须决定在智能体之间交换哪些上下文信息，而在多轮往返传递中往往会丢失关键细节。

- 子智能体泛滥（Subagent sprawl）：每个团队都发布自己的子智能体，导致企业最终堆积了数百个功能重叠的子智能体，既缺乏强制执行的统一标准，也没有明确的端到端负责人。

- 拼凑式提示词（The Frankenprompt）：每个团队都往系统提示词里添加一句话，最终导致规则相互冲突，且丧失了统一的沟通语调。

- 缺乏审核且过度局部的评测（Unvetted, overly localized evals）：每个人都添加仅针对自身子任务过度优化的评测集（Evals）。没有人拥有或维护全局评测集，管理层只能依据被稀释的、过度局部化的评分做出决策。

- 高延迟（Latency）：多智能体架构的复杂性显著增加了响应延迟。某位客户在将其多智能体运行框架（Multi-agent Harness）与单智能体循环进行对比评测时发现，后者的运行速度大约快了 2 倍。

## 采用具备渐进式披露能力的单智能体循环 (Using an agent loop with progressive disclosure)

上述“编排器-子智能体”设计确实是跨团队协调专家模块的一种合理思路，但往往更高效的方案是：通过技能（Skills）渐进式披露上下文，并通过工具搜索（Tool Search）渐进式披露工具。换言之，智能体在初始状态下仅看到技能与工具的简短描述，唯有在实际需要时才会完整加载其详细内容。

这一方案之所以行之有效，主要有以下三点原因：

- 共享上下文能够产出更优质的回答（Shared context produces better answers）：对于长周期运行的智能体而言，我们希望来自不同子任务的上下文能够留存在同一个主上下文窗口中。一个亲历了前面每一步执行结果的智能体能够将这些信息串联起来，从而产出比各子智能体传回的摘要汇总更加丰富、更具洞察力的结果。同时，这也意味着更少的上下文窗口切换和更少的有损交接（Lossy Handoffs）。

- 渐进式披露可防止上下文膨胀（Progressive disclosure prevents context bloat）：借助这一技术，团队可以构建出能够胜任广泛任务的单一智能体，而无需将所有上下文立刻加载到一段冗长的系统提示词中。这彻底消除了此前各团队不得不将工作拆分给多个子智能体的核心动因。事实上，针对更先进的模型，我们将Claude Code 的系统提示词精简了 80% 以上，其中就包括将大量内容改为通过技能和工具进行渐进式披露。

- 模型能力显著增强（Models are more capable）：从 Opus 4.5 开始，模型在单一循环中能够自主管理的复杂度远超大多数团队的预期。在 Opus 5.5 和 Fable 5.1 中，思考（Thinking）模式已不可关闭，且新一代模型越来越擅长在执行过程中主动叙述进度并自检工作成果，这使得运行框架（Harness）中的许多外部控制组件变得冗余。每一次模型升级，都允许你将更多的决策逻辑从外部框架移交回模型自身。此外，更精简的循环也更容易平滑升级到下一代模型——在我们协助客户完成的多次迁移中，僵化的多智能体结构往往正是阻碍新模型承担更多工作的瓶颈。

当然，单智能体循环设计需要严格的工程纪律：精心管理的系统提示词、能够在恰当时机精准触发的技能与工具描述，以及对上下文窗口、记忆（Memory）与笔记记录（Note-taking）的审慎处理。本文将在后续章节深入探讨迁移步骤与设计考量。

应当由一个中央团队统一负责端到端质量和系统提示词，并在每个新工具和评测集上线前进行严格把关。保持该中央团队精简有助于加快迭代速度，并降低大型组织内部的跨团队协调成本。

如果你确实需要采用多智能体路线，请从能够奏效的最简模式（如“生成器-验证器 Generator-Verifier”、“编排器-子智能体 Orchestrator-Subagent”或其他模式）起步。通过按上下文划分来有效解耦边界：为每个子智能体分配几乎不需要依赖系统其余部分的独立工作单元，并让其仅返回一个紧凑的结果（理想的候选场景包括：独立的研究路径、具备清晰接口的独立组件，或黑盒验证）。相反，当智能体按“问题类型”拆分时，它们就会陷入一场“传话游戏（Telephone Game）”，在反复的信息传递中每经过一次交接就会损耗一次保真度。

## 如何将子智能体并入主智能体循环 (How to fold subagents into the main agent loop)

许多团队在生产环境中已经运行着一套由编排器和若干专家智能体组成的系统。以下是我们建议逐步演进的目标单循环设计（Single Loop Design）：

- 单一模型与单一上下文窗口：运行一个开放式的工具调用循环（Open-ended Tool Loop），并在运行框架（Harness）中设置限制条件（如轮次预算、成本预算、写入门控 Write Gates）。

- 并行工具调用与自主决策：在每一轮（Turn）中，模型发出一批工具调用。运行框架并行执行这些调用，并将原始结果返回给同一个模型，由模型自主决定下一步行动：发起新一轮批量调用、向用户提问澄清，或是直接给出回答。当模型给出回答或触及预算上限时，循环终止。在给出回答后，还可以选择性地运行一次目标检查或验证器检查（Goal / Verifier Check）。

- 上下文内动态规划与即时修正：模型在第一轮将计划直接写入上下文中，并在收到执行结果时随时修正计划。这是相比“编排器+专家智能体”架构最核心的改变：制定计划的模型与执行计划的模型是同一个，因此它可以在执行中途随时调整计划。

- 上下文依然按需加载，但由智能体自主管理：

  - 不再需要专门编写代码步骤去根据规则目录重写计划，因为模型会自主决定每一步行动。

  - 执行顺序与领域操作规程（Domain Procedure）全部迁移至技能（Skills）中。

  - 硬性限制（如数据校验、审批门控 Approval Gates）以及对话中途出现的动态需求（如记忆检索Memory Lookup）全部迁移至工具（Tools）中。

  - 依然可以使用传统代码来预加载开销极低且几乎总是相关的信息（例如实体解析步骤 Entity Resolution），并在循环所调用的工具内部处理机械性工作（如构建请求载荷、解析流式输出、恢复澄清对话等）。

这种单循环设计同样有助于实现许多团队正在追求的终极状态（即构建一个能够理解用户高层级目标并代表用户自主行动的智能体），因为它将智能体所学到的一切都保留在同一个上下文中。

以下建议展示了团队如何分阶段从多智能体系统演进至单智能体循环，以及多个团队如何在这一过程中持续向该智能体贡献力量。

### 任务完成度评测 (Task-completion evals)

第一步是创建一个评测集（Eval Set），帮助你判断某个子智能体是否应当并入主智能体循环。在我们的实践中，行之有效的评测结构是：由中央团队拥有一套共享的端到端评测集，同时由各业务团队随其负责的每项技能（Skill）附带交付小型评测集。即便最初只有 10 个黄金样本（Golden Examples），也足以起步。

对照评分量表（Rubric）对智能体的最终消息进行打分，是追踪回答质量的良好起点。在系统仍保留编排器时，你还应当追踪路由准确率（它是否选对了子智能体？）。而一旦某个子智能体被并入主循环，则应改为检查智能体是否加载了正确的技能或调用了正确的工具。随着时间推移，逐步建立起“任务完成度评测（Task-completion Evals）”非常有帮助，因为在对比不同架构时，这一点最为关键。

在内部系统难以重放（Replay）、用户交互难以模拟的环境中，这项工作可能较为复杂。我们在内部行之有效的一种方法是在重要事件上记录时间戳（Timestamps），以便后续能够回放这些事件并作为定向评测来运行。

### 逐步精简子智能体 (Reducing subagents over time)

向单智能体循环演进的过程，本质上是将子智能体逐步转化为工具与技能的过程。这可以通过三种方式实现：合并领域子智能体、将子智能体作为工具调用，或用技能与工具替换子智能体。

![图 3：子智能体与主循环架构示意](/uploads/building-agents-folding-subagents/figure-3.png)

*图 3：从合并领域智能体、作为工具调用到彻底转化为技能与 MCP 工具的演进路径（对应原文图：folding in subagents）*

#### 1. 合并领域智能体 (Combining domain agents)

在进行第一次合并前，先构建一个小型端到端评测集。随后，从调用频率最高的子智能体开始，按照共享上下文（Shared Context）的原则进行合并。

优先合并那些在输出上彼此串联、访问相同数据，或经常被一起调用的专家智能体。例如，如果生产环境中有相当大比例的流量表现为“先调用某一个专家智能体，紧接着调用第二个专家智能体”，这就属于强耦合配对，是合并为单一领域智能体的理想候选。

#### 2. 将子智能体作为工具调用 (Subagents called as tools)

当前述需要保留子智能体的三个条件之一成立、且你决定保留某个子智能体时，一种行之有效的做法是让主智能体将子智能体作为工具来调用，以便主智能体能够继续保持与用户的直接对话。

我们仅在子智能体确需直接与用户交谈时，才建议采用完全交接（Full Handoff，即由子智能体接管整个会话）。除此之外的所有情况，都可以作为主循环中的“技能 + 工具”来实现。

这种模式允许你为子智能体定义统一的响应数据结构（Shared Response Schema），利用主智能体对照真实数据验证结论，并在进入最终综合步骤前精简输入内容。这是极佳的第一步，因为你无需重写现有的子智能体；同时，它还能在你决定是否将任何子智能体并入主智能体之前，为你提供任务完成度评测上的基准线（Baseline）。

不过，这种模式下仍会残留一些失效模式：

- 每个专家子智能体依然拥有各自独立的提示词、上下文、归属团队和评测集；

- 每次调用依然只传回一份有损摘要（Lossy Summary）；

- 每次调用都是一个嵌套的模型循环（Nested Model Loop），依然会增加延迟。

#### 3. 通过技能与工具将子智能体并入主智能体 (Folding subagents into the main agent via skills and tools)

每次将一个子智能体并入主智能体：将其提示词转化为技能（Skills），并将其 API 调用转化为 MCP 工具。对比保留该子智能体与移除该子智能体时的评测表现，然后再决定保留哪些、并入哪些。

在进行对比时，不要只看最终总分，务必仔细查看哪些具体任务的结果发生了翻转（Flipped）。当我们在一个示例客服智能体上测试这一操作时发现：将一个子智能体并入另一个智能体虽然降低了延迟，但却破坏了一个原本能够通过测试的流程——主智能体因为自己持有订单查询工具，便直接自行回答了用户，而没有再去向物流专家询问预计送达日期。

因此，在每次变更之前，请确保你的评测集中包含了针对生产环境中每一条协同运行的智能体调用链的测试任务，以及针对智能体绝不能违反的每一条规则的测试任务；并且每个任务都要运行不止一次，因为像上面提到的这种流程断裂，在两次运行中往往只会出现一次。

## 多团队如何协同共建单一智能体 (How several teams can contribute to a single agent)

领域推理能力可以从知识库（Knowledge Bases）、技能（Skills）和 MCP 工具中获取。各个独立团队可以将自己的所有权从“维护智能体”转移到“维护技能与工具”上，同时由一个小型中央团队保留对系统提示词和端到端质量的所有权——包括在新技能、新工具和新评测发布上线前对其进行审核把关。

### MCP 工具 (MCP tools)

当智能体需要执行动作、从系统读取实时数据，或以固定格式返回结果时，工具（Tools）是最合适的选择。在迁移期间，你也可以把工具作为继续调用现有子智能体的一种过渡方式。我们建议按用户意图（User Intent）对工具进行分组（而不是每个 API 对应一个工具），因为一旦系统提示词中的工具定义超过 30 到 50 个，模型的工具选择能力往往就会下降。

建议使用带有延迟加载（Deferred Loading）机制的工具搜索，减少硬性前置条件，并将任何必要的前置条件移入工具内部。例如，如果 Y 需要 X 的输出，那么 Y 的工具应当自行检查该输出是否存在，并在缺失时返回一条模型能够理解并据此采取行动的指令。按用户划分的权限控制（Per-user Permissions）也以同样的方式运作：每个工具负责检查当前调用用户可以查看或执行哪些操作，并在权限不足时返回模型可读的明确拒绝信息。这样一来，同一个主循环就能服务具有不同访问权限的用户，而无需为每个权限级别单独设置一个智能体。

### 技能 (Skills)

当智能体需要了解某个团队具体如何开展工作时——例如过去保存在专家子智能体提示词中的操作步骤、业务规则和判断准则——技能（Skills）是最契合的载体。

我们在扩展技能库时的做法是，将维护工作交还给编写这些技能的人。Claude 可以借助那些能够构建、测试和修剪其他技能的技能（元技能）来承担繁重的工作。

为了防止技能泛滥（Skill Sprawl），你可以让每个团队的直接负责人（DRI）各自负责本团队的技能，确保它们制作精良、职责清晰，并随附适当的评测集一起发布：

- /skill-creator：允许你编写从一开始就格式规范的新技能，并对现有技能进行审计，以对其进行精简、去重和结构重组。

- /skill-doctor：允许你查看技能库中每项技能的成本开销以及实际使用频率，并清理掉毫无用处的冗余部分（Dead Weight）。

### 知识库 (Knowledge bases)

对于智能体仅在部分时间需要用到的参考资料，知识库（Knowledge Bases）是最合适的选择。事实与参考资料（如公司政策、指标定义、产品规格）可以放置在供模型调用的搜索或查询工具背后，或者作为参考文件（Reference Files）随附在技能内部发布。请避免使用外部代码机械地检索这些上下文并将其直接粘贴到提示词中。

## 加速迁移工作的工具 (Tools to accelerate this work)

我们近期发布了一组 Claude API 技能，可以帮助完成上文提到的大部分工作。我们的迁移工具包（Migration Kit）将这些技能串联成一个引导式工作流，用于评估多智能体系统并将其迁移至单智能体循环。其中包含一个你可以在接入真实系统前先行试用的演示（Demo）：

- /claude-api build-eval：可帮助创建由中央团队拥有的第一套端到端评测集，或由各个团队随其技能附带发布的小型评测集。

- /claude-api prompt-audit：可自动标记出提示词、技能和工具描述中针对旧版模型编写的指令，并以差异对比（Diff）形式提出修复建议。你可以在系统提示词上运行它，找出那些曾为早期模型添加、如今却让智能体变得更慢或更僵化的规则；每个团队的 DRI 也可以在自己的技能和工具描述上运行它。

- /claude-api hillclimb：可对照现有评测集对应用进行迭代式自动优化。这可以用于“并入主循环 vs 保留子智能体”的对比评测（在将某个子智能体转化为“技能 + 工具”后，让它自动迭代优化技能和工具描述，检验并入后的版本是否能持平或超越原版子智能体），同样也可用于优化你的系统提示词。

- /claude-api cost-optimize：可剖析你的调用开销去向，并从提示词缓存（Prompt Caching）、裁剪非必要的输入与输出 Token、推理努力程度（Effort）以及模型选型等选项中，每次针对一项变更提出节省成本的建议。这有助于在给定架构设计下显著降低成本与延迟。

随着模型的演进，我们对如何最好地使用它们的理解以及围绕最佳实践的指导也在不断演进。这使得任何单一的架构都不如其背后的基本原则重要：量化评测，每次只改变一个变量，并保留经受住检验的方案（Measure, change one thing at a time, and keep what holds up）。

子智能体的去留正是这一原则的体现。随着模型能力越来越强、智能体运行周期越来越长，你现有的更多子智能体都可以转化为技能和工具。不过，你完全不必一步到位地完成这一迁移：先构建一个小型端到端评测集，每次并入一个子智能体，仅在并入后的版本得分更差时才将其保留为子智能体，然后周而复始、持续迭代。
