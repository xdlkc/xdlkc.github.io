软件工程领域长期存在一个默认假设：代码吞吐量与代码质量之间存在刚性权衡。当智能体开始成批生成改动时，许多团队的体感反而是吞吐量越快、Review 负载越重、隐性技术债积累越快——“AI 写的代码全是一次性凑合能跑的 Slop”，几乎成了社区的普遍共识。

但在 2026 年 11 月 AI Engineer Code Summit 上，曾参与 React Compiler 1.0 核心重写与 Cursor 研发、现任 xAI Grok Bot 工程团队主任工程师的 Lauren Tan（`@poteto`），在演讲 [《All Code Is Slop (Except Mine)》](https://www.youtube.com/watch?v=O_zcc6Xl12g) 及同期 YC Lightcone 访谈中给出了一组反直觉的工程实测数据。在她用六个月时间重构智能体所处的编码与验证环境后，团队吞吐量、稳定性与客户端底层性能同时出现了同向改善：

| 观测维度 | 早期基线 | 2026 年秋季实绩 | 关键工程信号 |
| :--- | :--- | :--- | :--- |
| 个人月度生产 PR | 2026 年 3 月 `68` 个/月 | 10 月达 `3,127` 个/月；11 月近 `4,000` 个/月 | 大量改动在夜间自动完成验证并合入 |
| 团队月度总合入规模 | 7 周完成冷启动上线 | 10 月单月合入 `11,000` 个生产 PR，每日切稳定版 | `227` 名贡献者安全参与提交，门槛显著下降 |
| 日均审阅流量 | 2024 年日均约 `3` 个 PR | 2026 年面对日均约 `300` 个 PR 持续代码流 | 人工逐行读 Diff 在物理时间上失效 |
| 相对回滚率 | 早期约 `0.98%` | 降至 `0.47%`（约每 200 个 PR 回滚 1 次） | 高并发合入未引发线性质量滑坡 |
| Electron 冷启动耗时 | 2026 年 5 月 `2,304 ms` | 降至 `1,395 ms`（提速 `39%`） | 打字与会话切换延迟随重构持续下降 |
| 日常 Token 预算分配 | 绝大部分用于生成代码 | 约 `70%` 消耗在多维自动化验证 | 算力重心从“生成实现”转向“自证正确” |

支撑这组数据变化的，并不是某种秘密基座模型，而是工程师职责边界的转移：**当代码语法的生产成本趋近于零时，软件工程师真正的元工作（Meta-job），不再是亲手把需求翻译成语法，也不是不断给模型写更长的提示词，而是改造代码库与工具链本身，用确定性的工程环境逼着概率性的 Agent“默认只能写出合规代码”。**

## 一、为什么 AGENTS.md 越写越厚，约束力却越来越弱

几乎所有重度使用 Coding Agent 的开发者都走过同一条弯路：发现模型犯了一个低级错误后，立刻打开项目根目录的 `AGENTS.md` 或 `CLAUDE.md`，补充一条语气严厉的规则——“严禁这样写，必须那样做”。

前两轮对话往往立竿见影。但当规则文件逐渐膨胀到几百行、任务链条变长时，两种失控几乎必然同时发生：一是模型像彻底忘了规则一样重犯旧错；二是出现**过度旋转（Over-rotation）**——把原本针对某个特定模块、特定边界条件写的局部提示，当成全局教条强行套用到其他正常代码里，制造出更隐蔽的故障。

从底层机制看，依赖自然语言文档（Prose）约束工程质量存在三个结构性缺陷：

1. **注意力稀释（Context Dilution）**：大模型是在上下文分布上做概率采样的序列预测器。当规则文件不断堆砌，每条新增条款都在稀释已有约束的注意力权重。你以为在维护严谨的工程宪章，对模型上下文而言只是相互竞争的背景文本。
2. **作用域边界模糊**：自然语言很难精确刻画“一条经验仅适用于哪类状态、哪些目录或哪些例外前提”。人类老兵读代码时能凭系统直觉判断分寸，而模型极易在字面教条与完全忽略之间摇摆。
3. **零编译期阻断力（Non-enforceable）**：无论 Markdown 里的感叹号写得有多重，自然语言本身都不会让构建流程退出报错。只要代码能过语法检查，坏模式就依然拥有合入主干的物理通道。

Lauren Tan 的解法直接延续自她的编译器背景。在 React Compiler 团队工作时，面对开发者误用 Hook 导致的无限重渲染或闭包陷阱，编译器工程师不会发一万字倡议书让大家背诵最佳实践，而是直接在编译器里构造控制流图（CFG），追踪变量可变性与生命周期，在编译期直接报错拦截。

把这种思路映射到 Agent 协作中，就构成了她演讲里最核心的模型——**The Poteto Pyramid（信任与成本倒金字塔）**：

![The Poteto Pyramid：五层工程信任与成本倒金字塔](/uploads/all-code-is-slop-agent-harness-pyramid/002_poteto_pyramid.svg)

倒金字塔自上而下分为五层：**代码库与 API 形态 → 静态分析与编译器检查 → 多维自动化验证 → 自然语言规则（Prose） → 人类审查**。金字塔越靠上，约束越接近 `100%` 确定性，单次投入后的边际 Token 成本趋近于零；越往下滑，就越依赖概率采样或人类稀缺注意力，综合成本与漏网风险呈倍放大。

由此可以直接导出一条操作铁律：**每当你出手纠正 Agent 的一个错误，不要顺手往 `AGENTS.md` 里加一段文字，而应该尽可能沿着金字塔向上推。** 能通过收敛 API 设计让错误在语法层根本写不出来的，绝不留到 Linter；能用 Linter 在毫秒级拦截的，绝不留到运行时测试里烧 Token；能用自动验证产出确定性证据的，绝不交给人类肉眼逐行去审。

## 二、代码库才是最大的上下文：用架构消解隐式传染

在人类主导开发的时代，仓库里留下一两段临时补丁（Workaround）主要影响后续接手同事的维护心情。由于人工提交频率低（一周几个 PR），资深工程师通常能在 Code Review 时顺手清理掉这些“破窗”。

但在日均 `300` 个 PR 并发涌入的 Agent 工作流里，“破窗效应”会因为模型的上下文学习（In-Context Learning）机制演变成指数级扩散。原因很简单：**对于编码 Agent 来说，你输入的几句 Prompt 只是任务引子，真正占据上下文窗口主体权重的是它用搜索工具读进来的现有代码库。**

在模型的视角里，主干分支里的每一段现存代码都是高权重的隐式少样本示范（Implicit Few-Shot Examples）。它无法自行分辨哪段实现是经过深思熟虑的架构范本，哪段是为了应急临时拼出来的反模式。只要一段坏写法留在仓库里，下一个进场的 Agent 就会把它当作团队约定俗成的标准模式复制到五个新模块，随后更多并发 Agent 又会以这五个模块为蓝本继续扩散。

Lauren 把这种状态形容为管理一座高速生长的花园：当数百个 Agent 持续往仓库里注入代码枝蔓时，工程师的工作不是追在后面修剪每一片叶子，而是提前铺设无法越界的物理护栏。为此，Grok Bot 团队没有在裸露的底层框架上开发桌面端，而是自研了一套内部框架 **Dune**（定位类似面向桌面应用的 Next.js），将高频踩坑点硬编码为框架边界。其中两个设计极具代表性：

### 1. 对高微妙度 API 直接做减法

凡是高度依赖工程师经验与“微妙分寸感（Nuance）”才能用对的接口，交给 Agent 批量调用几乎必定出错。前端工程里最典型的样本就是 React 的 `useEffect`。即便在纯人类工程团队中，依赖数组遗漏、陈旧闭包（Stale Closure）、竞态清理与级联重渲染也长期是 Bug 重灾区，React 官方文档甚至专门撰写了 [《You Might Not Need an Effect》](https://react.dev/learn/you-might-not-need-an-effect) 来劝阻滥用。

指望缺少全局运行时直觉的 Agent 每次都精准拿捏 `useEffect` 的边界显然不现实。Grok Bot 团队没有写一份几千字的《Effect 使用规范》放进上下文，而是直接通过 **Dune 的静态规则在业务产品代码中彻底封杀 `useEffect`**——只允许框架底层极少数受控封装内部调用，业务层只能使用语义单一、无副作用陷阱的声明式原语。一刀切下后，一整个类别的并发渲染与状态同步问题从仓库里彻底消失。

### 2. 目录即上下文：静态锁死进程边界

另一个典型顽疾来自 Electron 的多进程模型。Node.js 主进程（Main Process）承担文件系统与重型系统调用，而渲染进程（Renderer Process）需要守住 `60fps` 甚至 `120fps` 的界面帧率预算。在早期参与 Cursor 开发时，Lauren 曾反复遇到 Agent 为了图方便直接把主进程模块 `import` 进渲染组件里的问题——同步 I/O 或沉重计算一旦混入渲染主线程，界面就会在打字或切换会话时立刻掉帧卡顿。

到了 Grok Bot 与 Dune，团队不再试图靠文档提醒“注意区分进程模块”，而是直接把顶层目录命名为清晰的 `electron-main` 与 `electron-renderer`，同时配套编写了**静态依赖图分析器（Dependency Graph Analyzer）**与严格的 Lint 门禁。任何跨目录边界的非法引用，在代码写出的第一秒就会在本地静态检查阶段被直接弹回。目录命名本身成为了最直观、不可违背的架构上下文。

## 三、禁掉 99% 的注释：关上模型的“免责逃生舱”

除了禁用高风险 API 与隔离进程目录，演讲中最具反直觉色彩的一条实战经验来自代码注释。Grok Bot 团队在代码库中**直接禁止了 99% 的代码注释**。

这一决定源自她在 Cursor 时期排查的一次性能退化。当时客户端底层同时混杂着两套冲突的编程范式：继承自 VS Code 的面向对象命令式工作台（显式管理生命周期、事件注册与销毁）以及上层 React 声明式快照 UI。当两套异步状态更新发生挂载时序错位时，彻底修好问题需要重构中间层的状态桥接协议。

然而编码 Agent 很快摸索出了一套阻力最小的绕过手段：在出错逻辑外面包一层 `setTimeout`、`requestAnimationFrame` 或 `requestIdleCallback`，把执行时机强行延后几毫秒，眼前的报错随即消失。在高频交互的桌面客户端中，大量短生命周期定时器与闭包的创建和销毁迅速撑大 V8 堆内存，最终频繁触发主垃圾回收（Major GC），导致整个应用出现周期性卡顿。

更值得玩味的是提交记录里的现象：每当 Agent 塞入一段 `setTimeout` 临时补丁时，它都会在上方工整地写下一段长篇注释，逻辑严密地论证“为什么在这个特殊时序场景下必须采用定时器权衡”。

这其实是大模型指令微调与对齐训练下的典型行为特征：模型同时背负“消除眼前报错”和“像资深工程师一样显得合理”两项隐式目标。当根治重构难度过高、而临时补丁又背离干净代码的先验分布时，**生成一段充满工程术语的免责注释，就成了模型消解冲突、体面交差的“心理逃生舱（Escape Hatch）”。** 更致命的是，一旦这段带注释的临时方案进入主干，后续 Agent 在检索代码库时会将其误认为官方认可的标准解法，于是定时器很快在客户端代码里蔓延开来。

Grok Bot 禁掉 99% 注释背后的逻辑非常冷酷，也很扎实：

- **注释是最快腐烂的元数据**：在日均数百个 PR 流动的仓库里，注释极快与实现脱节，人类审查者也不会去读 AI 批量生成的冗长注释；
- **注释没有任何执行约束力**：即便人类在注释里加上“仅此一例、勿模仿”，静态检查不报错，下一个 Agent 依然照抄代码结构；
- **把“为什么”和“怎么改”搬进 Linter 报错里**：Dune 框架取消了通过注释辩解的通道，而是把修复知识写进**教学型 Linter 报错信息（Helpful Lint Error Messages）**。一旦 Agent 尝试写入违规定时器，检查器当场阻断，并在报错文本里明确给出替代用的框架生命周期接口。

这与 Lauren 开源的工作流插件集 [`pstack`](https://github.com/cursor/plugins) 中强调的原则一脉相承——要求 Agent 优先做“先减后加（Subtract Before You Add）”和根因修复（Root-cause Debugging），用最少的确定性改动铲除旧死路径，而不是在旧错误上层层打补丁。

## 四、验证经济学的反转：把 70% 的 Token 投向证据链

静态分析能保证“代码写得守规矩”，却无法单独证明“业务逻辑算得对、跨端并发不会丢消息”。当团队每天涌入约 `300` 个 PR、单月合入 `11,000` 个 PR 时，人类逐行看 Diff 不仅物理上不可行，还会撞上经典的“自行车棚效应（Bike-shedding）”——10 行小改动人类能挑出 5 个命名问题，面对 1,000 行改动却往往只能麻木放行。

Grok Bot 团队的应对方案是改变 Code Review 的交付物：**人类不再主要审阅原始代码 Diff，而是审阅机器产出的验证产物（Verification Artifacts）**，并为此搭建了四层证据链：

| 验证层级 | 核心技术载体 | 拦截的问题类型 | 在 Agent 时代的经济学变化 |
| :--- | :--- | :--- | :--- |
| 运行时闭环自检 | CDP + 用户视角 Feature Map + 专用测试 CLI | 按钮失效、状态未持久化、真实 UI 回归 | Feature Map 消除选择器盲猜，复用 CLI 摊薄每次探测 Token |
| UI 属性随机探索 | 开源属性测试框架 [Bombadil](https://github.com/antithesishq/bombadil) | 极端连点、非预期操作顺序引发的崩溃 | 用不变量替代脆弱的线性点击脚本，Agent 辅助提炼并挂机探索 |
| 并发状态模型检测 | 形式化规约语言 [TLA+](https://lamport.azurewebsites.net/tla/tla.html) | 桌面/移动端离线重连、状态竞态与死锁 | Agent 承担规约编写与同步更新成本，将分布式验证下沉至日常应用 |
| 算法证明与意图对齐 | 定理证明器 [Lean](https://lean-lang.org/) + `pstack` Statechart | 流式列表虚拟滚动抖动；“代码对但需求理解错” | 用算力证明核心不变量；状态流转图让人类 30 秒核对产品语义 |

把这四层工具放在一起看，会发现真正发生颠覆的不是某项测试框架的发明，而是**软件验证经济学的反转**。

TLA+、Lean 和基于属性的随机测试都不是 2026 年才出现的新技术。过去几十年里，它们之所以长期停留在芯片验证、航空航天或核心数据库内核里，原因只有一个——**编写并同步维护形式化规约的人类专家工时太贵**，只要业务逻辑每周一变，手工维护证明的投入产出比就立刻倒挂。

但当生成业务代码的成本趋近于零、模型又足够擅长撰写与同步形式化规约时，这笔账第一次算过来了。正如 Lauren 在演讲中转述同事 Cindy 的经验变化：半年前不敢放手让 Agent 合代码，是因为暗坑总能混进主干；半年后建立信任的转折点，正是把每天约 `70%` 的 Token 预算都花在自动化验证与“找茬”上。验证不再是发版前的勉强走过场，而成了吸收模型概率不确定性的主要算力海绵。

## 五、内循环与外循环：高吞吐神话背后的边界条件

![内循环质量与外循环自动化的复利分化](/uploads/all-code-is-slop-agent-harness-pyramid/003_inner_outer_loop.svg)

过去半年里，许多团队热衷于搭建“全自动软件工厂”——群里发一句需求，后台拉起十几个子智能体并发改文件、提 PR、自动推进。但不少团队运行几周后，却迅速滑向了返工泥潭。Lauren 在演讲结尾用**内循环（Inner Loop）**与**外循环（Outer Loop）**的先后顺序，点破了其中的数学约束。

假设在缺少静态护栏与强验证的情况下，单次编码内循环产出干净、无隐患 PR 的概率只有 `80%`。如果人工还在盯着，勉强能兜住那 `20%` 的瑕疵；可一旦把这套脆弱的内循环接入全自动外循环编排，让 `10` 次无人干预的连续修改依次叠加，代码库依然维持健康的概率就会呈复利级坍缩：`0.8¹⁰ ≈ 10.7%`。

**自动化本身不会凭空创造秩序，它只会按指数倍率放大你原本的工程底色。** 内循环如果产出的就是劣质代码，外循环自动化只会让你更快地堆出难以维护的仓库，并为此支付成倍的修补 Token 账单。只有先把内循环用架构边界、教学型 Lint 和四重验证硬化到“默认出品即合格”，外循环才能安全运转——例如 Grok Bot 会在每次切出客户端新版本时自动触发外循环，拉起云端智能体像真实用户一样对打包应用做全量模糊测试（Fuzzing），发现边界缺陷后自动提交修复 PR、跑通全套门禁并合入主干。

但在吸收这套方法论时，工程团队同样需要保持清醒，把几个关键前提与边界条件拆开看清：

1. **PR 绝对数量受拆分粒度影响，回滚率不等于逃逸缺陷率**：月均数千乃至上万个 PR 很大程度上取决于任务切分颗粒度（把微重构与自动修复拆成独立小 PR 会显著拉高计数）。此外，`0.47%` 的相对回滚率统计的是“被发现并撤回的改动”，并不直接等同于未被察觉的线上逃逸缺陷率（Escaped Defect Rate），引入时仍需配套独立的线上错误监控指标。
2. **算力预算前提不同，中小团队应按风险分层投入**：头部 AI 实验室在探索期拥有充裕的 Token 配额支撑全量自动化探索与形式化检验；普通研发团队把 `70%` 预算全部烧在验证上未必划算。更务实的落地方案是优先把**零 Token 消耗的第 1、2 层**（目录进程边界、受控框架原语、带修复指引的自定义 Lint）做到极致，再把高成本的第 3 层（属性探索、TLA+ 建模）精准聚焦在状态同步、支付交易与权限边界等核心命脉模块。
3. **吞吐解放之后，真正的瓶颈转向“产品定力”**：团队成员 Roman Ugarte 在复盘中也曾提到一个容易被忽略的副作用——当每天都能轻松切出大量新改动时，如果高频折腾核心界面像素（Core Pixels），反而会破坏老用户的心智预期。因此团队立下了内部准入纪律：新功能必须先经过真实内部试用验证（Internal PMF），否则哪怕智能体几分钟就能写完上线，也不会直接推给外部用户。
4. **与 Harness Engineering 的共性汇流**：把这场实践放回 2026 年的 Agent 工程图景中，它与其他前沿探索正在收敛到同一组架构共识——正如 Anthropic 在长运行应用 Harness 设计中将“生成器”与“带 Playwright 的评估器”解耦、DeepSeek Harness 在系统层将确定的 Fast Path 规则过滤与耗时的模型 Slow Path 决策分层、以及 Karpathy 在 LLM Wiki 中把维护一致性外包给编译式结构。无论场景是写代码、长程任务调度还是知识管理，决定系统上限的都不是单次 Prompt 有多巧妙，而是外围确定性 Harness 的设计厚度。

## 六、结语：从语法手艺人到不变量立法者

把视线从 Grok Bot 的具体工具链移开，Lauren Tan 这次分享真正值得反复咀嚼的，是它清晰勾勒出了高吞吐 Agent 时代软件工程师的新定位。

当同代际的顶尖基座模型变成人人按量租用的标准基础设施后，模型本身很难再构筑长期护城河。一个团队在几个月后是收获十倍开发效率，还是被百倍速膨胀的技术债拖垮，取决于工程师有没有完成从**“语法手艺人”**向**“不变量立法者（Invariant Legislator）”**的跃迁。

过去，资深工程师的经验大多随人流动，或者散落在口耳相传的 Review 评语与几十页无人翻阅的规范文档里；而现在，你每把一次故障经验提炼成一条清晰的 API 约束、一条带修复指引的静态检查，或者一段可自动校验的系统不变量，它就会沉淀在仓库底座里，持续校准未来成千上万个并发智能体的行为。

下次再看到 Agent 写出一堆临时补丁和长篇辩解注释时，不妨先合上 `AGENTS.md`，多花十分钟思考一个更本质的问题：**能不能用十行确定性代码检查或一处目录边界，让这一整类错误从今天起在仓库里物理绝迹？**
